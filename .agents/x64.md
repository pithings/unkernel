# x86-64 and i386 guest binaries

The guest's CPU is AArch64 only (a64.md). x86 binaries run through
user-space emulators inside the guest, started by binfmt_misc; their
output is arm64 code that kwemu runs like any other. There is no x86
front end in kwemu and no x86 syscall ABI in the kernel (A native front
end, below).

| Image | x86_64 | i386 | Installed by |
| --- | --- | --- | --- |
| Debian | box64 0.3.4 (trixie's package) | box64's 32-bit mode, box32 | `/usr/local/libexec/kw-binfmt` |
| Alpine | qemu-x86_64 | qemu-i386 | `/etc/kw-qemu` (guest.md, In the Alpine image; also riscv64 and arm) |

Alpine 3.24 has no box64 package, and box64 wraps glibc's libraries, so
Alpine stays on qemu-user.

## Debian: kw-binfmt

- kw-init registers `x86_64` and `i386` in binfmt_misc after the kw
  layer's rc has mounted it, with qemu's magic/mask pairs (ET_EXEC and
  ET_DYN) and no flags: the interpreter gets the binary's path as the
  program's `argv[0]` (a name found through PATH keeps its basename).
  Debian's own `/usr/lib/binfmt.d/box64.conf` is not read (no
  systemd-binfmt, no binfmt-support).
- `/usr/local/libexec/kw-binfmt BINARY ARGS...` reads `e_machine`. If
  box64 or the architecture's `libstdc++.so.6` is missing, it installs
  first: as root, or through `sudo -n kw-binfmt --kw-install BINARY` for
  another user, only with a default route, under `/run/kw-binfmt.lock`.
  Then it execs `/usr/bin/box64 BINARY ARGS...`. Without a network or root
  it fails with exit 126 and a message naming what is needed.
- The install adds the Debian architecture (`dpkg --add-architecture
  amd64`, and `i386` for an i386 binary), runs `apt-get update` when an
  added architecture has no package lists (the image bakes arm64's only),
  and then `apt-get install box64`, whose dependencies are `libc6`,
  `libgcc-s1` and `libstdc++6` for amd64 (9.8 MB of packages, 41 MB
  installed); for an i386 binary also those three libraries for i386
  (3.6 MB, 16 MB installed).
- Side effects of the install: every later `apt-get update` also fetches
  the added architecture's lists (about 10 MB each), and the arm64 libc6
  is upgraded to the version of the foreign one (multiarch needs them
  equal; the baked lists are older than the mirror's).
- More x86 libraries come from multiarch: `apt-get install NAME:amd64`
  (`:i386`). box64 0.3.4 finds them in `/usr/lib/x86_64-linux-gnu` and
  `/usr/lib/i386-linux-gnu`.
- The script sets `BOX64_NOBANNER=1` and `BOX64_LOG=0` unless the
  caller set them (on a terminal box64 otherwise prints its banner and
  every library it loads); errors still print.
- First use, CLI on an x86 host with the host's network, UP kernel, data
  disk (2026-11-25): an x86_64 binary 61-63 s (the list update is 15 s of
  it), an i386 binary first 86 s (both architectures). Afterwards a
  static x86_64 hello world takes about 125 ms per run and a dynamic i386
  one about 80 ms. Not tried on the page (Wisp).
- `uname -m` reports x86_64 under box64, also for an i386 program.

## What runs under box64

Checked in the Debian guest on 2026-11-25. The measurements and most
checks used sid's 0.4.3 unpacked beside the installed 0.3.4; the image
installs 0.3.4.

- Static and dynamically linked x86_64 programs, also with 4 CPUs.
  Outputs of the measured workloads matched native and qemu-user.
- box64's own tests (`tests/test01..38`, no 14): 34 of 37 pass on 0.4.3,
  30 of 37 on 0.3.4. Tests 11 (TLS self pointer), 36 (MXCSR rounding in the
  interpreter) and 38 (guest_alloc) fail on both, and the same way under
  qemu-aarch64 on an x86 host; 0.3.4 also fails 17, 30, 32 and 35 there
  too. None is a kwemu or kernel fault.
- V8 (Node 22, x64 build from nodejs.org) on 0.4.3: box64 detects
  self-modifying code by write-protecting translated pages and taking the
  SIGSEGV, which works here.
- **Wrapped libraries lag Debian's.** box64 replaces some x86 libraries
  with wrappers around the arm64 ones; for trixie's libsqlite3, liblzma
  and libcrypto3 the wrappers miss symbols, and the program jumps to an
  unresolved PLT entry (SIGSEGV at NULL). `BOX64_EMULATED_LIBS=libNAME.so.N`
  runs the x86 library instead (sqlite3 and xz work that way). The
  `openssl` command does not run; `sha256sum` and `md5sum` do.
- **No TLSDESC relocations** (`R_X86_64_TLSDESC ... not supported`): Node
  24's x64 build aborts, on both versions and on a real arm64 host too.
- A static busybox prints correctly and then exits 128 (also on a host).
- **box32 (i386) is weak.** A dynamically linked glibc hello world runs
  but its exit status is lost (0 instead of 7, on 0.3.4); a static musl
  one dies on `writev` ("Unsupported Syscall 0x92") in 0.3.4 and hangs in
  0.4.3. Both run correctly under Debian's qemu-i386 (in `qemu-user`,
  every qemu target: 64 MB to download, 491 MB installed). Real 32-bit
  applications are untried.
- 0.4.3 keeps translated code of large binaries (350 KB of it or more) in
  `~/.cache/box64` (DynaCache, on by default, about 13 MB for node and
  python); 0.3.4 has none. With it a warm `python3 -c pass` takes 1.6 s
  instead of 8.9 s, and `node -e 0` 7.7-9 s instead of 17 s. Moving the
  image to 0.4.3 means a package from forky or sid (it needs libc6 2.39,
  which trixie has).

## Measurements

2026-11-25, i7-10700K, Node 24, UP kernel, JIT on, 2 GiB, box64 0.4.3 with
DynaCache, qemu-x86_64 10.0.13, the machine shared with other work.
Median of runs 2-4, as multiples of the native aarch64 time in the same
guest:

| Workload | Native (ms) | box64 | qemu-user |
| --- | --- | --- | --- |
| CoreMark, 3000 iterations | 1326 | 2.3 | 5.8 |
| float loop (SSE against AdvSIMD) | 192 | 2.1 | 44 |
| zstd -3, 8 MiB | 526 | 2.4 | 11 |
| xz -6, 1 MiB (liblzma emulated) | 2083 | 1.9 | 5.4 |
| sqlite (libsqlite3 emulated) | 3039 | 2.4 | 9.5 |
| sort -n, 200k lines | 1412 | 1.9 | 7.3 |
| sha256sum (wrapped libcrypto) | 75 | 2.4 | 27 |
| `python3 -c pass` | 238 | 6.7 | 60 |
| python loop | 844 | 4.1 | 22 |
| dash spawning 40 `true` | 66 | 40 | 475 |
| `node -e 0` (Node 22) | 356 | 25 | 58 |
| node CPU script (V8's JIT) | 2122 | 5.8 | 24 |

- box64's arm64 code runs at native speed per instruction (490-630 MIPS)
  and executes more of them: 2-2.8 times native's count on compute, 5-7.5
  times on python and V8 (qemu: 7.5-61 times).
- Each box64 start costs about 17.7 M guest instructions (65 ms), each
  qemu-x86_64 start 137 M (780 ms).
- kwemu's JIT compiles and frees 5-30 times as often as for native code,
  but compile time stays at 0.3-1.7% of wall time and 89-93% of
  instructions run compiled. box64 chains blocks through a jump table, so
  each chained block is an indirect exit from compiled code: 27.5 M per
  CoreMark run against 1.5 M natively.
- 0.3.4 against 0.4.3 without its cache: CoreMark 2.76 s against 2.92 s,
  python start 7.8 s against 8.9 s. `BOX64_DYNAREC_CALLRET=1` took 0.4.3's
  CoreMark to 2.70 s and python start to 6.0 s; `BOX64_DYNAREC_BIGBLOCK=0`
  was slower on CoreMark (3.83 s); `BOX64_DYNAREC=0` (the interpreter) is
  about 90 times slower. `STRONGMEM=1`, `SAFEFLAGS=0` and `BIGBLOCK=3`
  changed nothing.
- 4 CPUs, zstd with 1 and 4 threads: native 620 and 331 ms, box64 1585
  and 894 ms, qemu 6663 and 4884 ms.

## A native front end

Not built. It would be a second kwemu front end (`src/x64`) on the
ISA-neutral core plus a per-task x86-64 user ABI in `arch/wasm` (a second
syscall table, thunks for the legacy syscalls arm64 lacks, `struct stat`,
the `O_*` values that differ, packed `epoll_event`, `sa_restorer`,
`arch_prctl`, clone's argument order, x86 signal frames and regsets).
The measurements above set what it has to beat: about 2 times native on
compute, where the gain would be small, and wrapped library calls, which
box64 runs as arm64 code. Its case is startup and process spawning (7-40
times native under box64), runtimes with their own JIT, and the
compatibility gaps above.

What x86 needs from the core that A64 does not:

- Instructions straddle pages, so a block can depend on two pages; v86
  ends a block before an instruction within 15 bytes of the page end.
- Revalidating a block compares up to 15 bytes per instruction.
- No instruction announces new code (A64 has IC IVAU): stores to
  translated pages must be tracked.
- TSO: plain wasm loads and stores are weaker than x86's ordering on an
  arm64 host, which matters with the SMP kernel only. box64 does not
  implement it by default either (`BOX64_DYNAREC_STRONGMEM`).

| Project | Licence | Use |
| --- | --- | --- |
| box64 | MIT (`x64primop.c` from x86emu, permissive; the Wine-derived files have no licence text) | flag formulas, PCMPxSTRx, SHA, AVX edge cases; four-pass flag liveness; `x64syscall.c` as a list of what differs; `tests/`; the lockstep check of interpreter against dynarec. Memory operands are host pointers and decoding is fused into per-opcode switches |
| v86 | BSD-2-Clause (SoftFloat BSD-3) | one opcode table generating decoder, analyser, JIT dispatch and tests; jump fusion over lazy flags; SoftFloat extF80 for exact x87. 32-bit only, full system |
| FEX-Emu | MIT | 2,291 assembly tests with expected registers (`unittests/ASM`); its x64 syscall layer with ioctl tables |
| Blink | ISC | a small readable interpreter, JIT and syscall layer |
| QEMU `target/i386` | LGPL-2.1-or-later | the table-driven decoder (`decode-new.c.inc`) for VEX and AVX |
| iced, Zydis | MIT | decoder tables, or a decode oracle in tests |
| Intel XED | Apache-2.0 | not for the kernel image: incompatible with GPL-2.0-only |

The MIT, BSD and ISC code can be copied or translated into kwemu with its
notices kept; the syscall ABI itself is best taken from Linux's
`arch/x86` (the same tree and licence). box64 and v86 do not accept
AI-generated contributions upstream.
